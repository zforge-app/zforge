# Zforge — regression coverage matrix

This matrix links `Documentation/Requirements/CURRENT-STATE.md` contracts to automated testing and verifications that depend on macOS. It describes **covering of scenarios**, not percentage of lines. Existing test means identified source; execution and result must be recorded separately. In a refactoring, add the characterization case before changing the corresponding area.

## Compulsory guarantee policy

Since **2026-10-04**, apply the [requirements RNF-Q01 to RNF-Q06](Documentation/Requirements/PRODUCT-REQUIREMENTS.md#quality-polishing-and-regression-prevention) and [test rules for agents](AGENTS.md#tests-as-a-behavioral-guarantee). The policy is normative; this documentary update does not add tests performed or solve the gaps of this matrix.

- For each changed functionality, relate requirement, use scenario (initial status → action → result), relevant unit tests/integration/UI and necessary visual or performance checks. It shall also cover shared state/handler consumers and adjacent affected flows.
- Corrections shall include a test that reproduces failure before the change and then passes; refactorings must preserve the previous characterization. Changes in the logic/expectations of existing tests require demonstrated disagreement with the specification and traceable justification. Infrastructure adjustments cannot reduce scenarios or rigor.
- Record what you actually executed, results, failures, ignored, environment and limits. Built approved, written only test or runner who did not initiate do not approve a contract. Visual checks and performance measurements have their own evidence.
- Regression introduced or reintroduced into consolidated functionality blocks the conclusion. Do not hide failures pre-existing or declare full warranty when the necessary verification remains pending.

## Criteria for use

1. Associate each change to a matrix line and point out the existing test, the new test or manual script executed.
2. Rotate the suite of the area, then the full suites, and register in the summary of the change the results with the execution path.
3. If an automation depends on Spotlight, PowerBox, Finder, Quick Look or drag between apps and is unstable in the runner, maintain deterministic test for the internal rule and register real manual validation. Do not mark as automated which has only been inspected or compiled.
