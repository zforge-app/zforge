## Project language

- **All documents, logs, and strings in tests in this project must be written in English**, regardless of the language used in the conversation. This includes generated documentation, log messages, test descriptions, assertion messages, and test fixture strings.
- Other languages may be used only for text localization, including tests that verify localized text, or when explicitly specified. The language of the conversation alone does not establish an exception.

## Mandatory quality and polish standard

Zforge values polished UX/UI, transition flows, performance, and code quality. **“Design is how it works”** is an implementation principle: appearance, interaction, response, and outcome form a single experience. The goal is to create a **“Wow effect”** through attention to detail and fluidity of use. These requirements apply to all agents when implementing new features, evolving existing features, refactoring, or fixing bugs; the requirements are consolidated in [`PRODUCT-REQUIREMENTS.md`](Documentation/Requirements/PRODUCT-REQUIREMENTS.md#quality-polishing-and-regression-prevention).

- **Polish every detail:** icons, animations, gestures, transitions, naming, placement and ordering of UI elements, sizes, translations, colors, and shapes must be intentional, consistent across equivalent surfaces, and compatible with native macOS conventions. Check alignment, spacing, hierarchy, readability, interaction areas, enabled/disabled states, focus, and feedback. A correct static appearance does not establish flow quality.
- **Polish the sequence of states:** verify entry, execution, completion, error, cancellation, and repeated execution of the action, as applicable. Fast navigation, selection, mode switching, opening/closing panels, and resizing must maintain visual continuity, correct state, and predictable responses, without unintended jumps, clipping, flicker, or publication of stale results. Respect accessibility and reduced-motion preferences; effects must not impair use.
- **Treat performance as an observable requirement:** preserve responsiveness during navigation, scrolling, preview, and file/archive operations. Avoid blocking work on the UI thread, unnecessary recomputation, and uncontrolled resource growth. For changes affecting performance, define the representative workload and acceptance criteria before making the change; compare latency, fluidity, and CPU/memory use against a reproducible baseline. Record measurements and limits instead of assuming improvement from inspection.
- **Preserve code quality:** maintain clear responsibilities, concurrency and engine isolation, shared components for equivalent behaviors, and readable, testable code. Do not duplicate state/handlers or introduce shortcuts that hide failures, weaken invariants, or make flows unpredictable. Refactoring must preserve the characterized contracts.
- **Validate under actual usage conditions:** follow the relevant matrix in [`UI-UX-GUIDE.md`](Documentation/Requirements/UI-UX-GUIDE.md#compulsory-polishing-of-experience), including all four modes when affected, single/multiple selection, applicable mouse/keyboard/gestures, supported widths and zoom, languages, themes, and accessibility. Visual inspection of the flow complements automated tests; neither type of evidence replaces the other.

## Tests as a behavioral guarantee

- **Every system feature must have detailed automated tests that express the interaction expected by the user and prevent regressions.** Derive scenarios from the specification, with an initial state, action, and observable results; cover the main path, alternatives, boundaries, errors, cancellation, persistence, and concurrency when applicable. Choose unit, integration, and UI tests according to the contract; testing only a calculation or directly calling a handler does not guarantee the gesture, focus, menu, or interface transition.
- Before changing an established feature, identify its contracts and tests, run the relevant coverage to establish a baseline, and add characterization where there are gaps. To fix a bug, create a case that reproduces the failure, verify that it fails for the expected reason before the fix, and that it passes afterward. Tests must verify the contract without reproducing the implementation as their own oracle.
- **Changing the logic or expectations of an existing test merely to make the tested code pass is prohibited.** A failure requires investigating the implementation and specification. Change the behavior required by the test only when it is demonstrated to conflict with the current specification, including after a change explicitly requested by the user. Identify the requirement, document the divergence and justification, and synchronize the contract, test, and implementation in the same interaction. Behavior observed in the code alone does not authorize redefining the expectation.
- Do not delete, disable, ignore, loosen assertions/tolerances, reduce scenarios, or replace tests with less rigorous checks to hide a failure. Infrastructure, fixture, or synchronization improvements are allowed only when they preserve the scenarios, expected results, and rigor of the checks; justify the change and demonstrate that these are preserved. If they modify the required behavior, apply the specification-compliance rule above.
- Tests must be deterministic, with controlled fixtures, isolation, and explicit synchronization. Investigate intermittency; do not use retries, arbitrary waits, or longer timeouts to mask a regression.
- Run the tests for the change and affected adjacent flows; changes to state, handlers, or shared components also require the regression suite that consumes them. Check the cases actually executed and record results, failures, skipped cases, and limits in [`REGRESSION-COVERAGE.md`](REGRESSION-COVERAGE.md). A green build, zero executed tests, existing test source, or a runner that did not start does not constitute functional approval.
- **Regressions in established features are unacceptable** when implementing a new feature, evolving an existing feature, or fixing a bug. A regression introduced or reintroduced by the change blocks completion: fix the cause and add automated protection without sacrificing the previous contract. Preexisting failures must also be identified and recorded, without hiding them or presenting them as approval.

## Criteria for completing a functional change

1. The delivered behavior matches the specification, and the relevant contracts and records are synchronized.
2. Tests represent expected usage and the risks of the change; new coverage and affected regression tests have been executed and passed, without losing previous guarantees.
3. The flow has been checked in the interface when there is a visual or interaction change, including relevant transitions and language, size, and accessibility conditions.
4. The code has been reviewed for clarity, isolation, and consistency; performance impacts have been measured when applicable.
5. Evidence distinguishes implementation, executed tests, visual review, and measurements. If a required check is blocked or pending, record the gap and inform the user of the limitation; do not declare the feature fully guaranteed or its polish validated. Historical gaps do not waive these rules or become resolved by this policy.

## Continuous contract maintenance

- **All application rules must be documented and kept up to date in `Documentation/Requirements`.** Whenever the user asks for something that changes an existing requirement, adds a new requirement, or fixes incorrect behavior, update the corresponding requirements document **in the same interaction, without requiring a separate documentation request**. Record the requirement even when implementation remains pending, identifying that status; when implementing or fixing it, synchronize the contract with delivered behavior and available evidence.
- In **every agent interaction with this project**, check the relevant requirements documents and keep them up to date in the same interaction. Immediately record new or refined requirements, decisions, behavior changes, and new evidence. If the interaction introduces no change to requirements or state, preserve the content without artificial edits.
- When implementing or fixing a feature, update the corresponding contract in `Documentation/Requirements` alongside the code; synchronize `TASKS.md`, `DIVERGENCES.md`, and `REGRESSION-COVERAGE.md` when the status, divergence, or coverage changes.
- Explicitly distinguish implemented behavior, planned requirements, historical notes, and pending verification. Do not declare a function ready based only on a plan, build, or static inspection. In a conflict, follow the user's direct instruction; for existing behavior, use `Documentation/Requirements/CURRENT-STATE.md` until the change is implemented and documented.
- Before completing a change, check adjacent flows that share state or handlers, especially all four modes, multiple selection, menus, toolbar, keyboard, preview, localization, and resizing. During refactoring, characterize affected contracts before extraction and record validation limits.
