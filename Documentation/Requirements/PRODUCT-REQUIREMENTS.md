The app and test targets use Swift 6 language mode in Debug and Release. Preserve the default `MainActor` isolation of the app and the concurrency configuration; pure functions can declare `nonisolated`, while AppKit interactions and UI callbacks remain in main actor.

## Product View

Zforge is a compressed file manager based on 7-Zip for macOS. The objective is to achieve the functional coverage of the 7-Zip File Manager of Windows, offering this capacity in a native, modern and integrated application to macOS.

The product must be treated as a complete application for managing compressed files and files, and not just as a minimal interface for compacting and extracting content.

## Quality, polishing and regression prevention

**Mandatory requirements defined in 2026-10-04.** They apply to all functionality and any new implementation, evolution, refactoring or correction. Its adoption does not prove integral care by the current code: the evidence and gaps continue in [`../../REGRESSION-COVERAGE.md`](../../REGRESSION-COVERAGE.md) and [`OPEN-REQUIREMENTS.md`](OPEN-REQUIREMENTS.md). The mandatory procedure for agents is [`../../AGENTS.md`](../../AGENTS.md#mandatory-quality-and-polish-standard).

- **RNF-Q01 — Integrated polish:** UX/UI, transitions, performance, and code quality make up the Zforge quality standard. “Design is how it works”: the goal of creating a “Wow effect” must come from a coherent, fluid, predictable, and polished experience. Icons, animations, gestures, transitions, naming, placement and ordering, sizes, translations, colors, and shapes must meet the observable criteria in [`UI-UX-GUIDE.md`](UI-UX-GUIDE.md#compulsory-polishing-of-experience), preserving native interaction and accessibility.
- **RNF-Q02 — Continuity and response:** each flow must preserve state, selection, and focus according to its contract when starting, completing, failing, canceling, repeating, or interleaving actions. Transitions must not publish stale content or cause unintended jumps, clipping, or flicker. Long operations must provide the expected feedback and cancellation while keeping the interface responsive.
- **RNF-Q03 — Demonstrable performance:** changes affecting performance must have a representative workload, reproducible baseline, and acceptance criteria defined before the change. Measure latency/responsiveness, CPU, and memory according to risk, including larger data volumes and repeated actions where relevant. Avoid blocking the UI thread, redundant work, and uncontrolled resource growth; a claim of improvement requires a recorded comparison. Degradation against an accepted criterion is a regression.
- **RNF-Q04 — Maintainable code:** preserve clear responsibilities, shared models and handlers, concurrency isolation, and the engine boundary. Keep code readable and testable, without duplicating state or bypassing failures by weakening invariants. Refactorings must preserve characterized contracts and their coverage.
- **RNF-Q05 — Representative tests:** every feature must be guaranteed by detailed automated tests derived from the specification, with an initial state, action, and observable result. Cover main paths, alternatives, and applicable risks involving boundaries, errors, cancellation, persistence, and concurrency; combine unit, integration, snapshot, and UI tests according to the contract (layers in RNF-Q08). Real gesture delivery, focus, and menu or sheet presentation require interaction evidence; menu contents, state transitions, layout, and appearance are proven offscreen. Builds alone are insufficient. Visual review of the flow complements automation, with recorded limits.
- **RNF-Q06 — Test integrity and absence of regressions:** do not change a test's logic/expectations to accommodate an incorrect implementation. Change required behavior only when a conflict with the current specification has been demonstrated, identifying the requirement and synchronizing the contract, justification, test, and code. Infrastructure adjustments must preserve scenarios, expectations, and rigor. Do not remove, ignore, or loosen checks to hide failures. Every fix must gain a reproduction test; regressions in established features block completion of new features, evolutions, or fixes until resolved. Required verification that was not executed remains pending, without a declaration of a complete guarantee.
- **RNF-Q07 — Build diagnostics:** a change must not introduce compiler or static-analysis issues. An unavoidable diagnostic requires a documented technical justification and explicit human review approval before accepting the change. Check actual build diagnostics; a successful build alone does not establish absence of issues. Preexisting tool diagnostics must be identified separately. **Commit gate (user decision, 2026-11-02, ZF-57):** a commit whose content builds with any warning or error is blocked. The versioned hooks `.githooks/pre-commit` and `.githooks/pre-merge-commit` (enabled per clone with `git config core.hooksPath .githooks`, shared by every worktree) run `Scripts/check-warnings.py`, which builds the git index — exactly what the commit contains, not the working tree — with `xcodebuild build-for-testing` on the `Zforge` scheme in Debug (app, Finder extension, unit and UI tests). Warnings in third-party Swift packages are listed without blocking; warnings without a source location (linker, build phases) block. Commits that only touch Markdown files or `Documentation/` skip the build. The build is incremental in a private copy inside the checkout's git directory, and a cached build never hides a warning found earlier. Bypassing the gate (`--no-verify`) requires the same explicit human approval as an accepted diagnostic.
- **RNF-Q08 — Test layers and selection (user decision, 2026-10-27):** XCUITest takes over the user's screen and is slow, so it is limited to what only real interaction can prove (gesture and drag delivery, keyboard shortcuts reaching the focused window, focus, real menu/sheet presentation, window lifecycle, system UI such as Finder), with one representative path per test. State, menu contents, per-mode/language/width/theme parity, layout, and appearance are covered offscreen by unit, integration, and snapshot tests (swift-snapshot-testing references under `ZforgeSnapshots/`). Each change runs the full `Unit` test plan and only the UI tests that the versioned impact map (`TestPlans/ui-impact.json`, applied by `Scripts/affected-tests.py`) links to the changed paths; unmapped source paths select `UI-Smoke` until mapped. `UI-Full` runs before releases or on request. Selected UI tests run offscreen by default (2026-11-01, ZF-56): `Scripts/affected-tests.py` runs them, unchanged, in parallel lanes through the `zforge-xcuitest-sim` tool, which intercepts XCTest's event synthesis and delivers the events inside throwaway copies of the app, so no app window, cursor movement or synthesized event reaches the user's screen; the script finds the tool next to the checkout or, from a linked worktree, next to the main checkout (2026-11-02), and `ZFORGE_XCUISIM` overrides both. The tool keeps menu tracking's keyboard-focus requests from reaching the window server (2026-11-02), so a simulated app never takes the keys the user types in another app. Offscreen runs do not use macOS Automation Mode (2026-11-02): testmanagerd turns it on system-wide (the "Automation Running" indicator and, after a while without UI tests, an authentication prompt in front of the user) for every session that uses its accessibility path, so `affected-tests.py` runs the lanes with the tool's `XCUISIM_NO_AUTOMATION_MODE=1`: XCTest's element tree, attributes and idle waits come from XCTest's own in-app engine through a direct port to the app, and XCTest's automatic screenshots (taken from the real screen) are off (`--automation-mode` goes back to testmanagerd); real UI runs still turn Automation Mode on. Each checkout builds into its own directory of the tool; the tests in `offscreen.realOnly` of the impact map (Finder, drag and drop through the window server, out-of-process open panels) run as real XCUITests afterwards, and without the tool every UI test runs real. An offscreen pass is UI evidence only for interaction kinds with recorded real-versus-simulated equivalence; pixel review and visual review still use real runs. Agents announce real UI test runs before starting them. Moving a check to another layer must preserve every assertion (RNF-Q06). UI test launches are isolated from each other and from the user (2026-11-01, D-63, ZF-54): a UI test launch (any argument starting with `--ui-`) never reads or writes the user's preferences. A test that checks persistence across launches names its own suite (`ZFORGE_UI_PREFERENCES_SUITE`); every other UI test launch starts from the defaults in a private suite (`ZforgeUIFixturePreferences`) cleared once at launch. One `ZforgeDefaults.application` serves the browser preferences, the sidebar favorites, the language lookup and the automation folders. AppKit's own state is kept out too: window and sidebar split-view frame autosave is turned off, and open panels store their state under their own `ZforgeUITest` identifier. The unit test host (the app XCTest launches for the `Unit` plan, recognized by `XCTestConfigurationFilePath`) is isolated the same way (2026-11-01, ZF-54): its own private suite (`ZforgeUnitTestHostPreferences`, cleared at launch), no window frame autosave, and no grants of the user's (stores default to `ZforgeDefaults.application`). The unit test host also stays out of the user's way (2026-11-02): it opens no browser window at launch (which, without grants, also asked for folder access in an open panel) and runs as an accessory app, outside the Dock and the app switcher (`UnitTestHostPresentation`); UI test launches and ordinary launches are unchanged. Windows that unit tests order in stay off every screen (for example at x = −10 000, kept there by not constraining the frame), so the `Unit` plan never shows a window in front of the user. Tests never read or write `UserDefaults.standard`; every suite a test creates is named `ZforgeTestSuite.<name>` and emptied when the test ends, and the first removal in a run deletes the suite files earlier runs left (cfprefsd writes a suite's file back when the host exits, so at most one run's files remain). Snapshot references the isolated host cannot write are attached to the result and copied into the project with `Scripts/export-snapshots.py`. A UI test that needs several windows gets them placed by the fixture, not by dragging a title bar (2026-11-01, D-70): `--ui-window-side-by-side` puts the first browser window at the leading edge and later ones at the trailing edge (`UITestWindowPlacement`), and the test asserts that they do not overlap before interacting across them. Unit tests share one main actor while suites run in parallel, and a time limit also counts the wait for it (2026-11-01, D-71): heavy fixture work (creating many files or folders) runs off the main actor, long main-actor work in a test yields between steps, and suites whose cases each lay out a whole window are `.serialized`; none of this removes a scenario or an assertion. A window a unit test creates in code is owned only by its Swift references (2026-11-09, D-81): it is made with `TestWindow.make` (`ZforgeTests/Support/TestWindows.swift`) or sets `isReleasedWhenClosed = false` itself, because AppKit's default makes `close()` release the window once more and crashed the test host when the extra release reached a later autorelease pool. Tests do not measure the main actor or the processor with wall-clock time (2026-11-09, ZF-68, D-86–D-89): another suite can hold the shared main actor for 10–16 s in the full plan, so a test waits for an event, a drained queue (`waitForIdle()`) or the other task's own end rather than a clock; a hang guard that remains counts only time in which the awaited work could run (attempts or polls of the actor that runs it, or a watchdog on another actor armed when the work becomes due); a performance gate in the `Unit` plan measures the work done (`WorkMeter`: retired instructions on a private executor), not elapsed time; a snapshot that shows a system-rendered image (the application icon in an alert) waits until it is rendered, not its placeholder. A UI test drag that starts a dragging session is performed as a person performs it (2026-11-10, D-92): `dragAndDrop(onto:)` (`ZforgeUITests/DragGestures.swift`) presses, moves onto the target, pauses there and releases, because XCTest 27.2 posts the move and the release of `click(forDuration:thenDragTo:)` within milliseconds, before AppKit's session has started or reported the target.


## Platform and native experience

- The application is aimed at macOS and must prioritize technologies, interaction patterns and native components of the platform.
- Use the modern and current macOS techniques and APIs whenever they are compatible with the project requirements.
- Apply the visual and interaction features of Liquid Glass in a way appropriate to the context, preserving readability, hierarchy, accessibility and usability. The effect must not only be used as decoration.
- The experience must look like macOS: menus, commands, keyboard shortcuts, toolbars, navigation, selection, drag and drop, windows, dialogs and operations feedback must follow the platform conventions.
- Any string that can be viewed by the user must be localized in String Catalog, including views, menus and commands, titles, buttons, tooltips, placeholders, accessibility labels, error messages, confirmations, and transient feedback. Do not insert text hardcoded interface outside the catalog; when producing strings outside SwiftUI, also respect the language chosen in the application preferences.
- The user-authorized localization expansion of 2026-10-11 targets 21 localizations: English, Brazilian Portuguese, Japanese, Simplified/Traditional Chinese, Spanish, French, German, Italian, Korean, Russian, Polish, Ukrainian, Turkish, Thai, Danish, Czech, Dutch, Swedish, Hindi and Bengali. Complete catalog coverage, preserved substitutions, system/manual language matching, persistence and actual native interface checks are required. Current delivery and gaps remain in CURRENT-STATE and REGRESSION-COVERAGE; machine-generated drafts are not independent native linguistic review.
- For browser items, do not offer `Command + X`: `Command + C` publishes the original `NSURL` directly in `NSPasteboard`, `Command + V` copies and `Option + Command + V` moves them with `FileManager.moveItem`.
- In the drag and drop, the origin declares support for copying, moving and aliases inside and outside the application. Follow the modifiers during interaction in a shared reference state with `DropDelegate`: `Option` copies, `Command` moves and `Option + Command` creates aliases. Within `performDrop(info:)`, immediately start loading each `NSItemProvider` before returning; only the completion and subsequent transfer may be asynchronous.
- Local items can be added to an existing archive by contextual action with destination choice or by direct drop in archive and in the internal folders of your browsing. The operation confirms the modification before saving and preserving the source files. Updating covers ZIP and 7z, whole or split in `.7z.NNN`/`.zip.NNN` volumes (ZF-83, 2026-11-17); spanned ZIP (`.zNN`) and RAR sets are read-only.
- ZF-30, implemented with regression tests: archives items replicate the entire presentation of the local drag. Out, copy by default and move with Option; in the archive itself, move by default and copy with Option. Movements that alter the original archive require fully operable confirmation by the keyboard. Internal reorganization of ZIP/7z single volume root and gestures real are recorded in [plan current](ARCHIVE-DRAG-DROP-PLAN.md), with validation limits separated from build/engine tests.
- When making UI/UX decisions, consider both casual and advanced users who expect efficiency similar to that of 7-Zip File Manager.

## Possible evolution for iOS and iPadOS — study future

The user's question about a port does not approve or implement mobile support; the current scope remains macOS arm64/minimum 26.0. Static linkage can be maintained: [Apple supports static libraries in XCFrameworks with platform variants](https://developer.apple.com/documentation/xcode/creating-a-multi-platform-binary-framework-bundle). The current `.a` macOS cannot be reused as iOS binary just because it is arm64. It will be necessary to compile the core/bridge for SDK and target of iOS device and separately arm64 simulator; audit sources, assembly and used APIs. XCFramework is a packing option, not a requirement for direct compilation in the project.

Preserve `ArchiveServing` and the domain as candidates for reuse; adapt AppKit, authorized access to documents, staging/metadata and life cycle. Set memory budget, dictionary and parallelism for real devices, resolve/investigate OR-11 and test long operations with [iOS/iPadOS background run APIs](https://developer.apple.com/documentation/BackgroundTasks/performing-long-running-tasks-on-ios-and-ipados). Workers outside the main thread do not guarantee execution after the app goes to background. The consumption measured on Mac does not set a safe mobile limit.

The future distribution must review LGPL 2.1/relinking, corresponding source, other snapshot licenses, subscription and iOS channel terms. The static choice does not eliminate these obligations or demonstrate legal compatibility with the App Store. There is no built or iOS/iPadOS test at this stage.

## Integration strategy with 7-Zip

The current backend is `NativeSevenZipArchiveEngine` with static link of 7-Zip 26.02 in the main executable. Exclusive arm64 support, macOS minimum 26.0, Objective-C++ bridge and execution in workers. Compilation does not depend on brother checkout, download during build or external executable. The UI remains on `ArchiveServing`; limits and replacement after validation are preserved. Since ZF-55 stage 1 (2026-11-02, D-73) the engine operates on the authorized files: archives and volumes are read in place, writes produce the updated archive once beside the original, and no copy of the archive is staged. Evidence and to-dos of release are `CURRENT-STATE.md`, ZF-21 and OR-10.

### CLI backend history — replaced by ZF-21

The recommended initial strategy was the GUI orchestrate the official `7zz` executable, packaged with the application, to list, compact, extract, test and modify files. This approach must accelerate the first functional version and keep the compression engine isolated from the interface.

This choice shall not attach the domain or UI directly to CLI syntax and textual outputs:

- Set a proper abstraction of file engine, with typed templates for items, properties, progress, warnings, errors and results.
- Implement CLI as the first backend of this abstraction, allowing you to replace it or complement it without rewriting UI.
- Keep the evolution open for a C++ helper native based on `IInArchive` and `IOutArchive` interfaces of 7-Zip when structured callbacks are needed, higher loyalty of names and properties, passwords without more precise interactive textual protocol or progress control.
- Run the `7zz` directly as a process, never by shell, and build the arguments as a typed list to avoid ambiguities and command injection.
- Separate stdout, stderr and progress; solicitar UTF-8 explicitamente; interpret output codes; prevent uncontrolled interactive questions; offer actual cancellation of operations.
- Do not include passwords in the case arguments. When the CLI backend is used, provide them by controlled stdin or another secure channel.
- Fix and test a known version of `7zz`. The distributed executable must be universal, embedded into the bundle, signed together with the application and compatible with App Sandbox and Hardened Runtime.
- Treat CLI outputs as a versioned protocol: keep parsers isolated, real fixtures and testing for large, encrypted, multivolume, unusual names, partial warnings and failures files.
- Access to files outside the container must follow the native user selection model and URLs or bookmarks with security scope. The helper shall receive only the necessary access to the operation.

CLI is therefore the initial backend and a useful process limit, but it must not be considered necessarily the definitive backend for all product features.

### Engine adoption phases

- In the initial phase of development, use is acceptable the ready build of `7zz` to validate features, flows and abstraction `ArchiveEngine`.
- The downloaded build shall not be distributed grossly or executed from an external installation. When incorporated into the application, you must lose the status of artifact downloaded in quarantine, receive your own helper identity, inherit the sandbox, be signed together with Zforge and participate in the verification and notation of the final product.
- For distribution outside the Mac App Store, sign all code nested with Developer ID, from the most internal component to the app, activate Hardened Runtime, notice the final artifact and attach the notation ticket.
- Do not assume that a `7zz` started as a child process automatically receives dynamic access granted to the application by opening panels, PowerBox or security-scoped URLs. During the CLI phase with App Sandbox, process inside the container and transfer the files through the Swift layer that holds the access, or explicitly validate another solution compatible with the distribution channel. This staging is acceptable for prototypes, but it is not the desired final architecture for large files.
- The planned evolution is to integrate and compile the official source code of 7-Zip available in `../../7zip` with static linkage, according to the preference explained by the user in 2026-10-02. The engine shall operate on the authorized files and use the interfaces of 7-Zip without depending on the textual protocol of the CLI. An isolated helper is an option independent of the type of linkage, not a requirement of this migration.
- The transition from built ready to engine compiled from source code shall not change domain models or UI; only the implementation of the `ArchiveEngine` backend.

### Backend native — 2026-10-02 decision, 2026-10-03 implementation

The production backend is compiled from the source code of the 7-Zip versioned for Zforge and connected statically, without running `7zz` or interpreting its textual output. The Zforge build must contain the native code for arm64 within a single application bundle. Preserve `ArchiveServing`, observable models, password and conflict flows, materialization limits and substitution of archives only after validation. The brother source code `../../7zip` is development reference; the reproducible build must not depend on the presence of this directory outside the repository or on downloading ready binaries. The CLI backend was removed from the composition and bundle; the status and engine validation limits native are `CURRENT-STATE.md`. [ZF-21](../../TASKS.md).

### Engine updates — decided 2026-11-10 (implemented with ZF-74)

- Keep the official 7-Zip sources vendored in `Vendor/7zip`, not as a Git submodule or a download during the build. Each Zforge revision then carries the exact engine source it builds, which the LGPL corresponding-source obligation needs, and builds offline.
- Change the snapshot only through `Scripts/update-7zip.py <tag>`. It imports an upstream release tag byte for byte (upstream export attributes do not apply), applies the patches listed in `Vendor/7zip-provenance.json` from `Vendor/7zip-patches/`, regenerates `BuildSupport/SevenZip/inputs.xcfilelist`, records version, revision, archive checksum and the matching reference `7zz` asset, and reports added and removed files, license file changes and the upstream history since the previous version. `--verify` checks the snapshot against its provenance; `--status` compares it with the newest upstream release.
- Keep the patch list empty when possible; a needed engine change goes to `Vendor/7zip-patches/` with its reason and is offered upstream.
- Commit an engine update on its own: the snapshot, the provenance, and only the bridge or build changes the new release requires. Behavior changes go in separate commits.
- Validate each update with a clean build without warnings, the full `Unit` plan, and the UI tests the impact map selects for `Vendor/*`; review the upstream history for the formats Zforge exposes.
- Cadence: a release that fixes a vulnerability is imported promptly and followed by a Zforge release; other releases are imported per upstream release or before each Zforge release. Once the repository is on GitHub, a scheduled workflow runs `--status` and opens an issue or pull request for a newer release (pending).
- The official `7zz` console binary is a development reference only (benchmarks, fixture generation and comparison). It is not tracked in Git: `Scripts/fetch-7zz.py` downloads the macOS asset of the vendored release recorded under `reference_cli`, verifies its checksum and reported version, and caches it under `~/Library/Caches/dev.zforge/7zz`.

## Functional mark: browser read-only

The first functional milestone of Zforge is a file manager native read-only. Until a later phase explicitly authorizes writing operations, the application must allow navigation, selection, inspection, sharing, Quick Look and opening, but do not copy, move, delete, rename, duplicate, create folders or edit compressed files.

- Each new common window starts at Recents. Visual preferences may persist globally, but the last path visited must not be restored.
- The first line of the sidebar is Recents, without category header, and opens a virtual list of recently used files provided by the Spotlight index.
- Recents displays each original file only once. Working copies under `temporaryDirectory/Zforge`, including archives sessions and operations, are not recent user files and must never appear or consume the result limit; Different files with equal metadata remain distinct.
- The actual directory of the user account is the first entry of Locations, out of Favorites, and uses the name of the folder as a label. The resolution of this path cannot use the Home redirected to the Sandbox App container.
- In “Go to Folder”, expand `~` and `~/...` with the real directory provided by `UserDirectoryService.homeURL`, never with `NSString.expandingTildeInPath` or another Home redirected by the Sandbox App.
- Desktop, Sidebar Documents and Downloads always represent the folders of the actual user account, never the homonymous directories within the application container.
- Breadcrumbs of file system locations display the entire hierarchy since volume, as `Macintosh HD > Users > felipe`, including when input occurred by sidebar. Ancestors added only for presentation cannot change history or produce empty columns in Columns mode.
- Windows opened from a file sent by Finder are dedicated to this compressed file.
- The interface offers Icons, List, Columns and Gallery, with sidebar for bookmarks, disks, removable volumes and mounted shares.
- Icons shows content previews by default for previewable files. Settings offers a persistent application-wide switch, independent of inspector visibility; disabling it restores file icons immediately. Preserve native folder/archive icons and use file icons when content is unavailable. Background thumbnail loading must be bounded, cancellable and independent of selection; archive thumbnails load automatically only within the thumbnail limits of D-73 (default 8 MB, measured on the solid block for solid items; see CURRENT-STATE §5), preserving explicit loading for other entries.
- Persistent access to locations outside the container uses security-scoped bookmarks. As Recents search for Home by Spotlight, the first common window must request authorization for Home when there is no bookmark; cancellation keeps an explanation with a clear action to try again.
- A sidebar observa mount, unmount e rename. The server connection covers `smb`, `afp` and `nfs` by means of the macOS flow; Bonjour discovery is not part of this milestone.
- The server connection action uses the visible name “Remote” in the sidebar, the Go menu, the help of shortcuts and the connection sheet, with translation “Remoto” in Brazilian Portuguese.
- Packages are treated like files. Aliases and symlinks are solved when opening and cycles must be stopped.
- Files hidden remain hidden by default and can be alternated with `Command + Shift + .`. When visible, icon, name and metadata use `55%` opacity in Icons, List, Columns and Gallery; selected hiddens use `72%`, without attenuating the selection background.
- The experience remains window independent and monitoring the current directory must preserve still valid selections after updates.

### Transparent navigation in compressed files

- Recognized formats appear as navigable containers in the same breadcrumb of the file system, including archives inside archives at any depth (D-98, ZF-80, 2026-11-16): an archive inside an archive is entered in place from a writable copy kept until its root archive closes, edited in place, and written back into the archive containing it when it closes, which is written back in turn when it closes, up to the archive on disk; in Columns, selection enters it only within the automatic preview limit of its volume. *(Historical: until ZF-55 stage 2 nested archives opened recursively within a configurable depth (1–10, default 5) and root archive size (256 MB–16 GB, default 1 GB); from ZF-55 stage 2 (D-73) until D-98 an archive inside an archive was an ordinary file that opened in a new window titled `outer archive › inner archive`.)*
- The initial backend is the `7zz` universal 26.02 embedded in `Contents/MacOS`. The root file and related volumes are copied to a temporary session before running CLI, because the helper must not depend on dynamic access of the sandbox from the main process. *(Historical: the static engine replaced the CLI, and since ZF-55 stage 1 it reads the authorized original in place; see CURRENT-STATE §6 “Safe opening”.)*
- Sessions are in `temporaryDirectory/Zforge/ArchiveSessions/<UUID>` and hold only materialized items. Previews, nested files and externally opened items are cleaned when closing the window or session; orphan directories with more than 24 hours are removed at next startup.
- *(Historical: automatic preview of internal items had a fixed 10 MB limit.)* Since ZF-55 stage 3 (2026-11-02, D-73), automatic previews and thumbnails of items inside archives follow the Settings limits (preview 32 MB–2 GB, default 512 MB; thumbnails 4–64 MB, default 8 MB; solid archives; removable and network volumes), measured on the solid block for solid items; above them, display metadata and the explicit action to load the preview. The limits do not apply to Quick Look from local files.
- Materializations of unknown size have a safety roof of 1 GB. For declared items, stop writing if it exceeds the reported size plus a margin of 1 MB. Confirm operations declared above 1 GB and provide progress and cancellation.
- Passwords remain only in memory during the session. Never include them in arguments, logs or persistence; CLI backend must provide them for stdin.
- Common double-clicked internal items are temporary copies read-only, preserve name and extension, receive the quarantine of archive root when existing and open in the default application. External changes do not return to the compressed file.
- The `7zz` process is started directly, without shell, with separate stdout and stderr. Cancellation starts with interrupt and uses end as fallback.
- The UI and the domain cannot depend on text of `7zz`; parser, command construction, cache and process must remain isolated behind `ArchiveEngine` to allow future exchange for a structured C++ helper.
