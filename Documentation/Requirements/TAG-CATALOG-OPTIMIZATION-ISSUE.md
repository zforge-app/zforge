# ZF-42 — Optimize durable tag catalog: reopen below 2 seconds with 10,000 tagged records and storage below 1.5 MiB

Status: open; the first two candidates are implemented and pass isolated Release latency/storage acceptance on 2026-10-06. Complete application acceptance remains pending. Created 2026-10-06; related: ZF-41, OR-19, D-43.

## Problem and measured baseline

The [existing benchmark](../Benchmarks/durable-tag-index.md#catalog-and-json-results) contains 100,000 visible files, exactly 10,000 tagged files sharing one label, and excluded hidden/package descendants. Three fresh cached processes perform zero recursive scans and preserve every expected record, but readiness takes 9.185–11.157 seconds (median 10.377 seconds). JSON loading takes a median 18.973 ms; saving the complete snapshot takes 13.268 ms. The persisted snapshot is 1,320,326 bytes (1.259 MiB) with a 77-byte fixture-root prefix. These are isolated catalog measurements, not complete application startup or 10,000 distinct label names.

Static inspection of `FinderTagCatalog.prepareDiscovery` shows that restoration publishes cached records and unconditionally enqueues every cached path in `pendingReads`. Metadata reads and visibility checks therefore repeat across launches even with reusable journal history. The measured difference between JSON decoding and overall readiness supports investigating this preparation path first; phase profiling is still required to attribute costs precisely.

## Required outcome and acceptance criteria

- Quiet, valid-cache reopening must reach fully reconciled catalog readiness in **strictly less than 2 seconds** with 10,000 tagged records. Preserve exact paths, label names and colors. Showing an old snapshot before reconciliation does not satisfy readiness.
- Settled persistent catalog storage must total **strictly less than 1,572,864 bytes (1.5 MiB)**, including retained journals, WAL, shared-memory sidecars and other catalog files. Record transient replacement/compaction peak separately; do not hide persistent sidecars by measuring only the main file.
- Use the same 100,000-file, 10,000-tagged-file fixture and fixed path-prefix length for a reproducible comparison. Run at least three fresh processes without concurrent benchmarks/builds/tests or system sleep; each accepted quiet reopen must meet the target. Record every sample, source hashes, CPU time, physical footprint and ten seconds of idle.
- Separately measure the signed sandboxed application from process launch to usable, reconciled catalog, with grants already available. Report application and isolated-catalog timings independently. Keep the existing app peak-footprint target below 130 MiB, bounded utility work, responsive UI and post-completion CPU below 0.5% of one core. Completion must leave no periodic discovery worker.
- Preserve authorization before restoration, separate Home/Shared grants, hidden/UF_HIDDEN/ancestor/package exclusions, local editing outside global scope, deferred retries, cancellation and conservative reconciliation when journal history is unavailable or invalid. A stale index cannot qualify merely because it opens quickly.
- Offline creation, tag edits, renames, deletion and directory visibility transitions must be reflected before readiness. Lost/dropped history, changed scope identity, corrupt/incompatible storage and interrupted updates require correct recovery. Records and processed journal cursors must remain one crash-consistent checkpoint.
- Add supplemental workloads with 10,000 distinct label names, multiple labels per file, longer paths, repeated edits and long sessions. Report these separately from the same-label acceptance fixture; do not imply that the existing benchmark measures distinct-label cardinality.

## Candidate solutions, in recommended order

1. **Profile and make valid-history restoration incremental.** Measure decoding, scope validation, visibility work, metadata rereads, historical delivery, publication and checkpointing separately. Start journal monitoring before reconciliation; restore only identity-matched authorized scopes, wait for historical delivery, and revalidate changed/deferred items or required subtrees rather than every cached record. Preserve conservative full reconciliation when guarantees fail. Apple's [FSEvents guide](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html) supports persistent event cursors and describes dropped-history recovery; it does not guarantee correctness of this proposed optimization. Characterize tag-only metadata notifications, permission changes and hidden ancestors before removing eager reads. The [local captured reference](../SwiftUI/contexts/coreservices-persistent-file-system-events.md) documents the current integration boundaries.
2. **Batch remaining visibility and publication work.** Share bounded ancestor-visibility results within one reconciliation batch, validate off the main actor, merge results once, and avoid repeated sorting or rebuilding equivalent dictionaries. Discard batch caches after completion and invalidate affected ancestors on visibility events. Profile before/after; do not retain visibility indefinitely or trade correctness for early readiness.
3. **Compact the snapshot while retaining atomic JSON initially.** Store each scope prefix once and encode relative paths; intern repeated tag names and reference compact IDs plus color values. Validate decoded paths against their authorized scope, version the schema and migrate atomically. The existing JSON already meets the size ceiling, so this is headroom and structural improvement rather than the first latency fix. Benchmark encoded size, migration, decode and crash recovery; do not assume a binary/compressed format is faster when JSON loading currently costs only 19 ms.
4. **Compare incremental persistence alternatives only after the startup bottleneck is addressed.** Prototype a normalized SQLite schema (scopes, relative-path records, interned tags, associations and journal cursors) with transactional delta writes. Compare ordinary tables and appropriate `WITHOUT ROWID` tables; SQLite documents potential space savings, but [its guidance](https://sqlite.org/withoutrowid.html) makes benefits workload-dependent. Compare rollback journaling against bounded WAL: [SQLite WAL documentation](https://sqlite.org/wal.html) describes extra files, checkpointing and growth/read-cost tradeoffs. A custom append-only delta journal plus periodic compact snapshot is another candidate, but requires generation identifiers, torn-write handling, atomic record/cursor updates and bounded replay/compaction. Select only a measured candidate that meets the combined size ceiling and preserves durability; no storage backend is selected by this issue.

## Release decision before broader correctness review — 2026-10-06

The first two candidates are implemented and tested. Earlier unoptimized median cached readiness is 2.150 s, with two of three final runs above 2 s; those failures remain recorded. The subsequent Release comparison gives combined readiness 0.711478 / 0.683182 / 0.648278 s (median 0.683 s), versus Release baseline median 14.166 s. All three pass isolated latency acceptance with exact records and zero recursive scans. JSON remains 1.259 MiB with no persistent catalog sidecars and meets the size criterion for this same-label fixture. Complete existing regression and bounded native UI checks pass; this Release round adds six benchmark invocations and a signed application build, not new unit/UI cases or broad equivalence testing. Full-application startup at scale, cold Release and distinct-label coverage remain pending. The issue is not closed.
